## [0.5.0] - 2026-09-05

### Added

- Collage Maker is built. Choose up to twelve pictures, put them in the order you want, and get one image back — arranged, drawn and encoded by your own browser, with nothing uploaded. Four arrangements: a grid as square as the count allows, a single row, a single column, and a feature that gives the first picture two thirds of the width and stacks the rest beside it. The gap between pictures, the colour behind them, the finished width and the output format are all yours; the height follows from the arrangement, so a taller collage makes a taller file rather than a squashed one. Cells are filled rather than fitted, which is why no cell arrives with two bars of background beside it.
- The preview is not a mock-up of the collage: it is the collage, drawn at full size and shown smaller, so what gets downloaded is the drawing that was already on screen. The pixel limits the other image Gizlets keep are checked against the whole composition rather than against each picture going into it, because twelve pictures that are individually fine still add up, and the canvas that fails is the combined one.
- Collage Maker is a Flow block, and the first one that turns several images into a single image. A flow now takes its ceiling from the combining block in the chain rather than from the category holding it — assembling pages and arranging a collage are different jobs with different numbers of pictures — and a block that combines says what it actually produces, so a collage block reads "one image" where the PDF block reads "one PDF". A recipe link carries the arrangement; the gap, the colour and the width are taste, and a link does not carry taste nobody chose.
- Crop Image is built. Drag a rectangle over the picture, or type its left, top, width and height in image pixels, and download just that part — decoded, cut and re-encoded by your own browser, with nothing uploaded and the uncropped original never leaving the tab. Aspect ratio presets lock the shape to a square, the two photographic ratios, widescreen, or any of those turned upright, and free crop takes whatever shape you draw. The selection is keyboard-operable in its own right: arrow keys move it, Alt with an arrow key moves it a single pixel, and Shift with an arrow key resizes it, keeping a locked shape as it goes. A selection that runs off the edge of the picture stops at the edge instead of collapsing, a zero-area one is refused with a reason, and the pixel ceilings the other image Gizlets keep are kept here too.
- Crop Image is a Flow block, so a chain can crop between any two image steps. A flow has nobody to drag a rectangle, so the block asks for a shape instead and takes the largest rectangle of it from the middle of the image — the same crop the workspace opens on when you pick that ratio and touch nothing else. A recipe link carries the shape, spelled `16x9` rather than `16:9`, because the link format's own delimiters are the reason it has never had to percent-encode anything.
- A `/roadmap` page says what Gizlet is building next and what would make it stop. Seven phases each fill in the same short form — when, what, what it reuses, the one signal Gizlet can actually watch, and the condition under which the work does not happen — so two phases can be compared by reading the same line twice instead of by trusting two differently shaped paragraphs. There is no timeline, connector, dot, gantt or card anywhere on it, and that is the point: every one of those shapes implies a date this project does not have, and a reader who infers one has been misled by the layout rather than by the prose. A phase's "when" is a dependency; the only statuses are behind us, next, and later. It ends with a table of four things Gizlet will not build, each carrying somewhere else to go, closing on the rule that generates the list: if it needs a server, it isn't a Gizlet.
- The Gizlet index now shows the bench. "Not built yet." — not "Coming soon", which promises — lists twenty-five Gizlets grouped by category with a count each, on dashed rules against the solid ones the working Gizlets use. A row on the bench is not a link, so there is no whole-row pointer inviting anyone to a page that does nothing; it carries exactly two, the phase that explains the order and a request that turns a reader into the one signal this project can count. A working Gizlet's row now prints its registry number, which is what makes the em dash beside an unbuilt one mean something. The request line is the last thing on the page, and it says plainly that a request opens a public GitHub issue in your name, and that we count issues rather than clicks.
- Asking for a Gizlet from the bench is one click. The row's link names it, the form resolves that name against the registry and prefills the idea field from the registry entry, and the issue takes a fixed title so demand is countable by a title search rather than by reading issue bodies. A name the registry does not carry is ignored outright rather than echoed back: the prefill ends up in an issue filed in the visitor's own name, so a crafted link must not be able to put someone else's text there. Rewrite the idea and the request becomes your own, titled as one. The value never leaves the browser, and query strings are not logged.

### Changed

- `design.md` is at version 1.1, with six amendments that bring the design system in line with the product that exists. Availability is now its own axis rather than a second meaning for the green `● LOCAL PROCESSING` badge: `PLANNED` and `WON'T BUILD` are mono, uppercase, dotless, and never green, because whether a Gizlet runs on the device says nothing about whether it exists yet, and a Gizlet that does not exist yet has no locality to report. The numbered tool row finally says what its number means — the registry id, zero-padded, treated as a shipped-Gizlet credential that the rendering withholds from a planned entry in favour of an em dash, which is a rule about what a row shows rather than a claim that planned entries have no id, since the registry requires the field and a test asserts the ids are unique. `/privacy`, `/roadmap`, and a planned Gizlet's placeholder page carry no ad in any placement: a page whose content is how we would know to quit loses its argument the moment an ad rail sits beside it, and it is the page most likely to be screenshotted and quoted. Document-shaped pages are a fourth layout type alongside the homepage, the tool page, and the Gizlet index — 38rem measure, Georgia headings, mono label columns, 2px section rules, no cards, no sidebar, no rail. Humour, subtle and occasional everywhere else, is barred outright from kill-criterion lines and the won't-build table, where wit reads as a pre-emptive apology for the decision. And Gizlet Pro is gone from the document, as it has been gone from the home page since it was hidden: there is one Gizlet, ads included, and nothing in the product may describe a tier that does not exist.
- Two of those amendments contradict what the site renders today, and the document says so where it states them rather than leaving the next reader to find out. `/about`, `/privacy`, and `/terms` render through `LegalPageLayout.astro` at a 48rem measure with 1px rules, which is a deviation from the document pattern rather than an exemption from it, and `/tools/` prints no row number at all, which the pattern's own "often" permits.
- Nothing on the site now describes an unbuilt Gizlet as working, and the compiler keeps that rather than a convention keeping it. A registry entry is either available, with an implementation behind it and an agent-facing description of what it reads and writes, or planned, with neither and no locality claim at all — locality is a claim about an implementation, and an unbuilt Gizlet has none. An unbuilt Gizlet's page renders no advertisement in any placement, stays out of search results and out of the sitemap, publishes only the breadcrumb trail rather than markup announcing a free working application at that address, recommends nothing, and appears in no search suggestion, no home page row and no other Gizlet's related list.
- The machine-readable catalogue now describes the plan as well as the product, which reverses an earlier rule deliberately: a catalogue that lists only what exists cannot answer "is this coming?", and the honest answer to that is more useful than silence. `/tools.json` publishes unbuilt Gizlets under their own `planned` key and `/llms.txt` under its own heading, both saying outright that nothing there is available. The shape omits the locality field, the input and output descriptions, and the privacy sentence rather than publishing an empty or false value for each: nothing claims locality, nothing denies it, and a reader is never asked to work out that a key name means "do not call this", because the fields that would let it be called are simply absent.
- A kill-criterion label reads on a dark background as well as a light one. `--warning` joins `--success` as a themed token with a lighter dark-mode value, so the one line on the site that says what would make us stop is not the hardest line to read.

## [0.4.1] - 2026-09-04

### Added

- A Gizlet Flow can start from a PDF. The category chooser above the chain offers PDF alongside Images, so the documents on the device can be merged, split, and turned into pictures in one pass: `Merge PDF → Split PDF`, `Split PDF → PDF to Image`, or a merge whose pages come back out as images. Nothing new was taught to the flow graph — Merge PDF, PDF to Image, and Split PDF each declared a PDF as their input when they shipped, and the workspace was the only thing that could not offer them a document to read. It is the chain 0.4.0 described and no visitor could build. Each document is opened by this browser as it is chosen, so the list shows its page count and refuses a locked or damaged file before a chain is built on top of it, and that costs `pdf-lib` alone: the flows page still fetches no PDF renderer until a run has something to draw. A merge says that one PDF is not a merge rather than leaving a button that does nothing, and switching category clears the chain, because a chain assembled for images cannot read a document and half of one would be a flow nobody assembled.
- A category appears only while a published Gizlet can begin it, derived from the starting payloads in `src/data/tool-flows.ts` rather than listed anywhere, and a recipe link carries the category it was built in. A link written before this release names none, which is exactly what an image flow means, so every recipe already shared still opens as the flow it was.

### Fixed

- A flow that ends by making a PDF no longer asks for the format of a file it never writes. The control was shown whenever any block re-encoded an image, and named the wrong thing twice over: a chain ending in Split PDF called it the "final output format" while handing over a set of documents, and every chain ending in a PDF offered WebP, which `pdf-lib` cannot embed and re-encodes as JPEG — a second lossy pass bought for nothing. Whether the control appears, what it is called, and which formats it offers now come from one tested function reading what the chain actually ends by producing: a chain that finishes with a document asks for the page image format and offers the two formats a PDF page carries as it is, JPEG and PNG; one that finishes with images keeps all three; and a chain that re-encodes nothing, such as a merge, has no format to choose. Adding a PDF block to a chain set to WebP moves the setting rather than leaving one the run would ignore, and a recipe link naming WebP for such a chain still opens, with the format the chain can honour.

## [0.4.0] - 2026-09-04

### Added

- Gizlet Flows can turn a document back into images. A chain that reaches PDF to Image converts every page, runs each later block once per page, and finishes with a set: a row per image with its own download, and one archive holding all of them, so the promise of one download at the end still holds. It needed no edit to the flow graph — the Gizlet declares `pdf-file` in and `image-file` out, and the payload-kind rule already said what that means. A Gizlet that reads a document is reachable after Image to PDF, with a merge the exception, because there is nothing to join a lone document to.
- A splitting step in the flow contract, the counterpart of the combining step Image to PDF and Merge PDF declare. A chain knows whether it ends with one file or a set because the step says so, rather than because the payload kinds were read as implying it, and the last step of either kind is the one that decides — so a chain that takes a document apart can combine it again, and the rule that keeps a merge out of a chain holding one file needed no exception written into it.
- A recipe link can carry a PDF to Image block, including its resolution. Which pages to convert is deliberately not carried: every other value in the format is a whole number or one of a closed list of names, and a page range would be the one key that could hold free text, so a shared flow converts the whole document.
- A Merge PDF Gizlet: choose two or more PDFs, arrange them, and download one document holding every page of every file in that order. Each document is opened by this browser as it is chosen, so the list shows its page count before anything is joined, and pages are copied rather than redrawn — text stays text, a scan keeps its resolution, and a merged document may hold pages of different sizes. Nothing is uploaded, which is the point: the documents people join are usually the private ones, an identity paper with a proof of address, a payslip with a bank statement. A password-protected PDF is refused by name, because its pages would copy as ciphertext without the password, and so is a file that is a PDF in name only. One merge takes up to 20 documents and 500 pages, the same 500 the PDF Viewer will open, and reports its progress past 50. The merged file is drawn in the page before it is downloaded, with pdf.js arriving only once there is something to draw. It needed no new dependency: `pdf-lib`, already here for Image to PDF, copies a page tree as readily as it writes one.
- A PDF is now shown in the page before anything is downloaded, both on the Image to PDF Gizlet and in a flow that ends in one. The result panel draws the assembled document page by page, with previous, next, and a page jump, so the page order, the page size, and what automatic orientation did to each sheet are all visible while there is still time to change them, instead of having to download the file to find out. It is the finished document that is drawn, not a re-rendering of the source images, and the page turning is the shared `src/scripts/pdf-page-view.ts` the PDF workspaces already use. pdf.js is loaded only once a PDF exists, so neither page's initial JavaScript changes for a visitor who never makes one, and a preview that will not draw says so and leaves the download alone, because a document can be perfectly good even when drawing it is not.
- A PDF to Image Gizlet, at `/tools/pdf-to-jpg/`: open a PDF, choose the pages, a JPEG, PNG, or WebP format, and 72, 144, or 216 dpi, and get one image per page. The document is drawn beside the controls while the pages are being chosen, so a page can be found rather than guessed at, and every page arrives with its own download alongside a single archive of the whole set. Reading the PDF, drawing each page, encoding the images, and packing the archive all happen in this browser, which matters because the pages people most often need as pictures — a scanned contract, a medical letter, an identity document — are exactly the ones that should not be handed to a conversion site. It is called PDF to Image rather than PDF to JPG for the reason Image to PDF was renamed: it writes three formats, and naming one of them would be the same inaccuracy in the other direction. A password-protected PDF, a file that is not really a PDF, and a document that reports no pages are each explained rather than left as a dead button, and one hundred pages is the ceiling for a single pass.
- `pnpm run pr:assets -- <image>…` publishes a pull request's screenshots to the `pr-assets` branch and prints the markdown that embeds them. The screenshot rule in [AGENTS.md](AGENTS.md) already said where those images live; getting them there by hand was a dozen git plumbing calls, rediscovered on every pull request. The script checks nothing out and switches no branch, and commits on top of what the branch already holds, so another pull request's images survive.
- A Split PDF Gizlet, at `/tools/split-pdf/`: open a PDF and either name the ranges you want — `1-3, 5, 8-10` gives three documents — or ask for every page separately and get one PDF per page. The document is drawn beside the field while the pages are being chosen, so a range can be found rather than guessed at, and each part arrives with its own download alongside a single archive of the whole set. The pages are copied rather than redrawn, so what comes out is the same PDF content it went in as: text stays selectable, fonts stay embedded, and nothing is re-encoded. Splitting is usually the step before sending part of a document on, which is exactly when the file on the device is a contract, a payslip, or a medical letter, so reading the PDF, writing each new document, and packing the archive all happen in this browser. A range that runs backwards, a page past the end, or the same range written twice is refused rather than guessed at, and a password-protected PDF, a file that is a PDF in name only, and a one-page document that has nothing to split into are each explained rather than left as a dead button. Documents of up to 500 pages, the same 500 the PDF Viewer will open, so anything this Gizlet produces can be read in the one next to it. It needed no new dependency: `pdf-lib`, already here for Image to PDF and Merge PDF, copies a page tree out as readily as it copies one in.
- Gizlet Flows can now split a document mid-chain. A flow carries a set of PDFs rather than a single one, so a Split PDF block takes the document apart into its pages and every block after it runs over each piece: images can become a PDF, be split back into pages, and be converted to images again in one pass. A set of documents finishes as one archive, the same way a set of images already did.
- `src/data/zip-archive.ts`, a ZIP writer of about a hundred lines, so a Gizlet that makes a set of files can offer one download. The entries are stored rather than deflated, because a JPEG, a PNG, or a WebP is already compressed and deflating one spends time to save nothing — which is what lets the format be written without a compressor and without a dependency. Every entry carries the same fixed 1980 timestamp instead of the clock, so an archive built twice from the same files is byte for byte the same and the download says nothing about when or where it was made.

### Changed

- Changelog entries are now written as one file per change in [changelog.d/](changelog.d/), instead of as a new line under `## [Unreleased]` in `CHANGELOG.md`. Every open pull request was editing the same lines of the same file, so the changelog conflicted on almost every rebase, and resolving it by hand is exactly the kind of merge that quietly drops someone else's entry. A new file cannot conflict with another new file. `pnpm run changelog:collect` assembles them into the release section at release time and deletes them, `## [Unreleased]` becomes a pointer to the directory, and the entries themselves are unchanged: same voice, same bullets, same place in the released changelog.
- `pnpm run changelog:draft -- --write` now writes one fragment per drafted entry into `changelog.d/` rather than appending to `CHANGELOG.md`, and never overwrites a file that already exists, so it can be re-run on a branch whose entries have already been rewritten. `--since origin/main` narrows it to the branch in hand.
- The Convert Image Gizlet's description now names the formats it takes, on its card, in its metadata, and on its regenerated preview card: “Convert JPG, PNG, WebP, AVIF, and BMP images to another format in your browser.” The previous wording, “common file formats”, left unanswered the one question a converter is asked.
- A flow can no longer be built with one combining step after another. Merge PDF declares `pdf-file` in and `pdf-file` out, so the payload-kind rule would offer it as the block after Image to PDF — but the payload reaching it there is already the single document that step made, and there is nothing to join a lone document to. `isValidFlowSequence` now refuses that arrangement, and the flow builder works out the next block from the whole chain rather than only from the block before it, so Merge PDF has a real flow contract without appearing as a block that could not work. An image flow therefore still ends at the PDF it makes unless a later block takes that document apart again, and Merge PDF's contract holds for a flow that starts from several PDFs.
- The JPG to PDF Gizlet is now called Image to PDF, accurately reflecting that it accepts JPEG, PNG, WebP, AVIF, and BMP images. Its `jpg-to-pdf` URL and recipe-link slug remain unchanged, so existing links continue to work.
- `openLocalPdf` now takes the wording for a document that will not open, so each PDF Gizlet says what to do about its own job. The reader tells you a locked file needs an app that can ask for its password; the converter tells you to save an unlocked copy and convert that. The mapping from pdf.js failures to sentences stays in `src/data`, where it is tested without a document or a worker.
- Pull requests that change something a visitor can see now carry screenshots, and a before-and-after pair when the change replaces something that already existed. [AGENTS.md](AGENTS.md) records where the files live: on a `pr-assets` orphan branch, never in `main` or in the change's own diff.
- Page turning in the PDF workspaces now comes from one module, `src/scripts/pdf-page-view.ts`, rather than being wired separately in each. It imports pdf.js only as a type, which is what lets Image to PDF reach it without shipping the library.

### Removed

- The PDF Viewer block in Gizlet Flows, announced in 0.3.0. Adding it printed one status line and showed the visitor nothing: the flow runner carried the document past it untouched, because viewing a result is what a result panel does rather than a pipeline step — no flow needs an Image Viewer block to see an image. Now that the panel previews a PDF, the block has nothing left to do. The `passesInputThrough` contract that described it is gone with it, and a Gizlet that reads and writes nothing another Gizlet can use says so in `flowlessToolSlugs` rather than claiming a pass-through contract, so the guard that catches a Gizlet which forgot its contract still catches one. The PDF Viewer Gizlet itself is unchanged. A recipe link written by 0.3.0 that names `pdf-viewer` as a step is now ignored whole, which is this format's documented behaviour for a recipe it cannot read; no alias is kept, because the window is one release long and the block never ran.

### Fixed

- `pnpm run changelog:draft -- --write` no longer fails with `Unknown argument: --`. pnpm 10 forwards its own argument separator to the script, which the script then read as a flag it did not recognise, so the documented invocation had never worked. Both changelog scripts now ignore it.
- Searching for an image conversion no longer sends people to Image to PDF. Its `png to pdf`, `webp to pdf`, `avif to pdf`, and `bmp to pdf` keywords made it match `jpg to png` — the keyword Convert Image declares for itself — on every term, and the connector `to` scored three times over, once for its name, once for its description, and once for its keywords. It outranked the converter on the converter's own query, and was the only result for `webp`, `avif`, and `bmp`. Connector words are now dropped from a query before it is scored, an exact keyword phrase earns the same kind of bonus an exact name match already did, and the three image Gizlets declare the formats they genuinely accept. `jpg to png` and `avif to jpg` rank Convert Image first; `png to pdf` still returns Image to PDF alone.
- The Image to PDF page's format question no longer asks “or only JPG?”. The Gizlet stopped claiming to be JPG-only when it was renamed, so the question raised a doubt its own page no longer invited.

## [0.3.0] - 2026-09-03

### Added

- A JPG to PDF Gizlet, and with it a PDF category: choose JPEG, PNG, WebP, AVIF, or BMP images, put them in the page order you want, pick A4, US Letter, US Legal, or a page fitted to each image, and download one PDF with one image per page. It assembles the document in the browser, so the passports, bank statements, and signed contracts people turn into PDFs are never uploaded. A JPEG or PNG page is embedded byte for byte; a WebP, AVIF, or BMP page is re-encoded as a high-quality JPEG first, because that is what a PDF can carry. One document holds up to 100 pages, each image is held to the pixel ceiling the Resize Image Gizlet already enforces, and past 20 pages the Gizlet says it is building a big document rather than looking stalled.
- A PDF Viewer Gizlet: open a PDF and read it page by page, with a thumbnail per page, previous and next, a page jump, and zoom from 50% to 300%. Every page is drawn onto a canvas by this browser, so it works the same on a phone — where most browsers refuse to show a PDF inline and download it instead — as on a laptop. The document is never uploaded, which matters for the payslips, tenancy agreements, and passport scans people would otherwise hand to an upload-a-PDF site to read them. A page opens fitted to its column and is redrawn at each zoom step rather than stretched, so text stays sharp. A password-protected PDF, a file that is not really a PDF, and a single page the engine cannot draw are each explained rather than left blank. It cannot select or search text yet, and says so.
- Gizlet Flows can end by making a PDF. A chain that reaches JPG to PDF takes several starting images in a reorderable list, runs every earlier block on each of them, and combines the results into one document — one page per image, in the order shown — with page size and orientation on the block itself and one download at the end. Removing the PDF block resolves the extra pages and says which image it kept, rather than dropping them quietly.
- PDF blocks in Gizlet Flows. The PDF Viewer is the first Gizlet that reads a PDF, so a chain can now end `… → JPG to PDF → PDF Viewer`. It needed no change to the flow graph: the viewer declares `pdf-file` in and `pdf-file` out, and the payload-kind rule below did the rest. Its contract also declares itself an inspection step, so a flow runs it and carries the same document forward untouched.
- A `pdf-file` payload kind in the flow contract, so every image Gizlet now hands its result to JPG to PDF and each links to it from its related Gizlets.
- A recipe link can carry a PDF flow, including its page size and orientation. The format gained closed-list values alongside its whole numbers, so the settings-only guarantee is unchanged: every accepted value is still one of a fixed set of names, and no key can carry file content, a filename, or a URL.
- `pdf-lib` as the project's first runtime dependency besides `astro`. There is no browser API for programmatic PDF creation — no platform equivalent of writing a page tree and embedding an image — so condition 1 of the dependency policy in [docs/architecture.md](docs/architecture.md) is genuinely met rather than asserted. It is pure JavaScript with no worker and no WASM, is imported only from `src/scripts/pdf-generation.ts`, and ships only on the JPG to PDF page.
- `pdfjs-dist` as a runtime dependency, with no dependencies of its own. There is no browser API that parses and renders a PDF, and the native alternative — handing the file to the browser's own viewer — does not render inline on iOS Safari or most Android browsers, so it cannot be the basis of a viewer. It ships only on the PDF Viewer page, and its 1.2 MB worker is fetched only when a PDF is actually opened, not when the page loads.

### Changed

- Flow compatibility is now derived from the payload kinds a Gizlet declares, rather than from a per-Gizlet `nextToolSlugs` list. That list only restated what the `input` and `output` contracts already said and could drift from them. A block is offered when it accepts what the block before it produces, so declaring a Gizlet that reads a PDF makes it available after JPG to PDF, and one that turns a PDF back into images makes the image Gizlets available after itself — with no edit to the flow graph. Covered by tests that run the graph over contracts the catalogue does not have yet.
- The flow builder's step dropdown lists Gizlets in tool-registry order, and no longer from a hardcoded array of image slugs. The visible order of the first three options changes as a result.
- A flow's starting image is now decoded when it is chosen rather than when the flow runs, so an unreadable file is refused before a chain is built on top of it.

### Fixed

- The home page now has its own 1200x630 preview card instead of falling back to the brand board. The brand board is 1536x1024, 1.79 MB, and a collage of small screenshots, so a Google result or a chat unfurl for the site's most important URL rendered as noise. The new card is drawn by the same script as the Gizlet cards, and its category line comes from the registry so it cannot advertise a kind of Gizlet that does not exist. The brand board stays the fallback for pages that have no card yet.
- The home page's meta description no longer repeats its own title. It opened with the title verbatim, so Google discarded it and assembled a snippet from the page's visible text — the eyebrow, the heading, and the intro paragraph, read as three stitched fragments. The description now names what the Gizlets actually do. Both title and description moved into `src/data/home-page.ts` with tests asserting they share no phrase, that the description fits the length a result shows, and that its local-processing claim holds only while every published Gizlet is local.

## [0.2.0] - 2026-09-03

### Added

- A Gizlet Flow can now be shared as a recipe link: `Copy recipe link` writes the chain, its order, and each step's settings into the page's URL fragment, and opening that link rebuilds the same flow. Settings travel in the fragment rather than a query string, so they are never transmitted to a server at all, and only whitelisted setting keys exist — no key can carry file content, a filename, or a URL. A link that does not parse and validate is ignored whole rather than partly applied.
- [docs/signals.md](docs/signals.md), recording which signals Gizlet can measure and which it cannot. Cloudflare Web Analytics supports no custom events and does not log query strings, so completions, error rates, downloads, and click-through are unobservable, and a plan that needs those numbers has to restate its criteria or change the data contract first. Linked from `AGENTS.md` and [docs/privacy.md](docs/privacy.md).

### Fixed

- The home page's search field no longer suggests searches that find nothing. Two of its three examples returned no Gizlet — one named a tool that does not exist, and one was phrased in a way the search cannot match — and the examples now live in `src/data` with a test asserting each returns an available Gizlet, so they cannot drift as the catalogue changes.

## [0.1.1] - 2026-09-03

### Added

- A `TODOS.md` recording deferred work with the condition that would revisit it.

### Changed

- Gizlet pages now choose their workspace from a registry-derived slug map and decide on launch status before the slug, so a planned Gizlet reaches the placeholder by rule rather than by falling off the end of a chain of conditions. Adding a Gizlet without a workspace, or without a related-Gizlet entry, now fails `pnpm run check` instead of crashing the production build.
- The JSON Formatter's processing sentence moved from the tool page into `src/data/tool-page-status.ts`, so the copy comes from the data layer like every other registry-backed claim.

### Removed

- The Gizlet Pro strip on the home page, and the "Pro" links to it in the header and footer. Gizlet Pro does not exist, and the strip described it in the present tense — the same class of untruth as an inaccurate local-processing claim. It returns when there is something to return to.

### Fixed

- The Gizlet Flows page is now listed in `sitemap.xml`. It was linked from the header but absent from the sitemap, so the page that chains Gizlets together was invisible to crawlers and answer engines.

## [0.1.0] - 2026-09-03

### Added

- A documented release procedure in [docs/releasing.md](docs/releasing.md), covering the ordered steps, the rule that a tag never disagrees with the changelog and the version, and what to do when a release has to be re-cut.
- A `pnpm run changelog:draft` script that drafts changelog entries from the Conventional Commit titles since the previous tag, previewing by default and only ever appending beneath hand-written entries.

- A browsable `/tools/` index that groups every available Gizlet by category, linked from the header, footer, and tool-page breadcrumbs.
- A page for unknown addresses that lists every working Gizlet and links back to the home page, replacing an empty response.
- A recorded pre-launch accessibility, performance, search-visibility, and UX audit of the production site in [docs/launch-audit.md](docs/launch-audit.md).

- Privacy-conscious aggregate analytics through Cloudflare Web Analytics, measured at the Cloudflare edge with no analytics script, configuration, or event calls in the site itself.
- Local JSON-LD Generator Gizlet for Product, Organization, Article, LocalBusiness, Event, and BreadcrumbList markup with live previews, copy actions, and separate validation guidance.

## Release policy

- Releases use `MAJOR.MINOR.PATCH` version numbers.
- Before `1.0.0`, a minor version may introduce breaking changes; patch versions are for backward-compatible fixes.
- The first usable public release will be `0.1.0`.
- Changelog entries describe user- or contributor-visible changes. Internal maintenance that has no meaningful external impact does not need an entry.
