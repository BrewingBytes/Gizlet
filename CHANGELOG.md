## [0.9.0] - 2026-09-07

### Added

- **Base64 Encode & Decode** turns text or a small file into Base64 and turns Base64 back into whatever it was. Both alphabets are here — standard, with `+` and `/`, and URL-safe, with `-` and `_` — along with the choices that usually go unmentioned: whether to write the `=` padding, whether to break lines at 76 characters as email does, and whether to wrap the result as a `data:` URI.
- **Decoding needs no settings.** It works out which alphabet it is looking at, ignores whitespace and line breaks, understands a `data:` URI prefix and reads the media type out of it, and copes with missing padding — which is how a JWT's middle section is written and the combination most tools get wrong.
- **When a decode fails it says which character and where.** A character outside the alphabet, an `=` with something after it, padding over data that has been truncated, or a length no encoder could produce: each is named with its position rather than reported as "invalid input". A last character whose unused bits are not zero is mentioned rather than refused — `QQ==` and `QR==` decode to the same single byte, but only the first is the canonical spelling, and the bytes are not in doubt.
- **Bytes that are not text are offered as a file.** Half of what anyone decodes is a picture or an archive, and the honest response is a download named after the type the data URI declared, rather than a screenful of replacement characters.
- The page says plainly, where it cannot be missed, that Base64 is not encryption. It is a way of writing bytes down, anyone can read it back, and this page reads it back.
- Written over bytes rather than handed to `btoa` and `atob`. `btoa` refuses any character above 255, so an é or an emoji fails outright; `atob` is lenient in exactly the places where a person needs to be told what is wrong. Both alphabets, the padding, and the errors live in one tested module instead, checked against the vectors in RFC 4648.
- **File Hash Generator** reads a file on your device and gives you its digest five ways at once — SHA-256, SHA-512, SHA-384, SHA-1 and MD5 — each one copyable, so you do not have to know in advance which one the person on the other end will ask for.
- **It also checks a hash you were given, which is the half people actually have.** Paste the checksum into the expected-hash box and the answer comes back as a word — match, or no match — with both hex strings underneath as the evidence rather than as the answer. Nothing to configure: the digest is worked out from the length of what you pasted, since 32 characters is MD5, 40 is SHA-1, 64 is SHA-256, 96 is SHA-384 and 128 is SHA-512.
- **Paste the checksum however you copied it.** A bare hash, a whole `sha256sum` line with the file name still attached, the tagged form BSD tools and `certutil` write, or the same thing in capitals. A line written for a different file warns rather than failing, because that is usually a rename. A whole SHA256SUMS file is refused with a note to paste the one line you meant, rather than guessing which of forty you had in mind.
- **What a match proves is on the page, not in the FAQ.** It proves the file is the file that hash was made from, and nothing about where the hash came from: if you copied it off the same page as the download, whoever could replace the file could replace the hash beside it. A no match names the four things it could be — a damaged download, a different version, a different build, a replaced file — instead of picking one.
- **SHA-1 and MD5 are computed and labelled broken.** Both can be given a deliberate collision, which is the attack a checksum exists to notice, so neither proves nobody meddled. They are here because a great many release pages still publish one of them, and refusing to read yours would not make it any safer.
- MD5 is the digest browsers refuse to provide, so Gizlet's own — written for the UUID versions that are defined in terms of it — does that one. It stops at 128 MB, above which the four SHA digests still appear and the MD5 row says why it is empty.
- Your file is read and hashed in your browser and never uploaded, which matters more here than on most pages: the files worth checking are installers, disc images and backups, and a checksum service that wanted the file would be asking for a copy of everything you were about to run.
- **JWT Decoder** takes a JSON Web Token apart and tells you what is in it: the header and the payload as indented JSON, and every registered claim explained one line at a time. `iss`, `aud`, `nbf` and `azp` are not guessable, and looking each one up in RFC 7519 is the work this page is meant to save.
- **It does not verify, and it says so where it cannot be missed.** Checking a signature needs the issuer's key — a shared secret typed into the page, or a public key fetched from the issuer — and neither belongs on a page that sends nothing anywhere. The signature is shown and measured, never checked, and the page never calls a token valid.
- **Dates twice over.** `exp`, `nbf`, `iat` and `auth_time` are given as the raw seconds the token wrote and as a UTC moment with how far away it is, and the token's own expiry window is reported against your clock. A date written in milliseconds — `Date.now()` rather than `Date.now() / 1000`, the commonest mistake in a hand-rolled token — is called out instead of being displayed as the year 57000.
- **A broken token is named by segment.** An encrypted token is identified as a JWE with five parts rather than blamed on its Base64; a two-part token is reported as truncated or unsigned; a segment that is not Base64URL, or not JSON, or JSON but a list, each say which segment and what is wrong. A payload that will not decode no longer hides the header that read perfectly well.
- **The things a token can be wrong about without being unreadable are notes, not refusals**: `=` padding a JWT should not carry, `+` and `/` from the standard Base64 alphabet, a missing signature under a real algorithm, `alg: none` with a signature attached, an expiry before the issue time.
- Paste the token with whatever it was copied out of still attached — an `Authorization` header name, a `Bearer` prefix, quotes from a line of JSON, line breaks from a log. All of it is ignored, and the page says what it ignored rather than silently rewriting your input.
- Your token is decoded in your browser and never sent anywhere, which matters more here than on most pages: a JWT is usually a live credential, and a token inspector that kept a copy would be an efficient way to collect other people's sessions.
- **Timestamp Converter** turns a Unix timestamp into a date and a date back into a Unix timestamp, both boxes live as you type. Every moment is given in UTC and on your own clock, each with its weekday and how long ago it was, alongside ISO 8601, seconds and milliseconds — all copyable, since the reason for looking one up is that it has to go somewhere else.
- **It will not guess whether your number is seconds or milliseconds.** The same ten digits are a moment in 2026 read as seconds and a moment three weeks into 1970 read as milliseconds, so the unit is a control you set. When the size of the number disagrees with it, the page says what the other unit would read and leaves your setting alone — because a converter that quietly overrules you is one you cannot use to confirm that some other system got the unit wrong.
- **A written date gets the same treatment.** `2026-09-07 14:30` is two different instants in London and Bucharest, so which clock it was read off is a choice too, with your device's offset shown on the control. An offset written into the text — `Z`, `+02:00`, `-0500` — is used instead, and the page names the offset it used.
- **Impossible dates are refused by name.** There is no month 13; February 2026 has 28 days, so there is no 30th; a day runs 00 to 23; and `23:59:60` is a leap second, which is real and which no calendar here can hold. Nothing is parsed by the browser's own date reader, whose idea of a valid date differs between browsers, so the answer does not change with the browser.
- Timestamps before 1970 work in both directions, and the range runs to the year 275760 at either end, which is as far as a date reaches in a browser.
- Your dates are converted on this device, by its own clock. Nothing is sent anywhere and no time server is contacted.
- **The date sentences are now written once.** JWT Decoder and Timestamp Converter both have to render a moment in UTC and say how far away it is, so `UTC` rendering and the `in 3 days` / `2 hours ago` wording moved into one module both read — which is why a token's expiry and a converted timestamp are worded identically rather than nearly so.
- **UUID Generator** makes identifiers in every version a browser can honestly produce — 4, 7, 1, 6, 3, 5, and the Nil and Max values — one at a time or a thousand at once, from your browser's cryptographic randomness and never from `Math.random`. A GUID is not a different thing from a UUID, so the braces and capitals are offered as a way of writing the same 128 bits, alongside canonical form, no hyphens, and a URN.
- It also reads one. Paste a UUID in any of those styles and the page says which version and variant it is, when it was made if it carries a time, and — for a version 1 — whether the node in it is a real MAC address or a random one. That last question is the difference between a version 1 that identified somebody's machine and one that did not.
- **A version 1 made here cannot leak a MAC address.** A browser cannot read one, so the node field is random with its multicast bit set, which is what RFC 9562 requires of a node that is not a network address — and it means the value says so to anyone who reads it back.
- **A batch of version 7s comes out in order, not merely near it.** A millisecond is long enough that forty made at once would share every ordered bit and differ only in randomness, so the twelve bits after the timestamp carry the monotonic counter RFC 9562 provides for exactly that case.
- **Versions 2 and 8 are explained rather than faked.** Version 2 substitutes a POSIX user or group id into the timestamp, and a browser has no POSIX identity — generating one would mean inventing the field that gives the identifier its meaning. Version 8 is free-form and says nothing without bytes its caller supplies. The page says so, which is more use to whoever came looking than a convincing fake would be.
- Version 3 needed MD5, which `crypto.subtle.digest` refuses outright and correctly. Rather than add a dependency, it is written out in `src/data` and tested against every vector in RFC 1321 — including the million-character one — in the manner of the CRC-32 and the EXIF reader already there. Versions 3 and 5 reproduce the published known-answer vectors, so they interoperate with other implementations rather than merely agreeing with themselves.

### Changed

- The roadmap's text phase now says that the file-digest Gizlet will also check a digest against one somebody published — which is what its registry entry has promised all along, since it has always been described as the way to "check a download is the file it claims to be". Computing a hash and checking one are the same computation with one extra field, so they are one Gizlet on one page rather than two routes to the same arithmetic.
- The phase also records a piece of reuse it had not: the MD5 written by hand for the UUID versions, because the browser's own crypto refuses to provide one, is the same MD5 the digests need for the checksums that are still published as MD5.
- The agent guides now say that a Linear issue defines a unit of work, and that its description is the one that counts. The GitHub issue linked from it is a mirror, often written before the scope settled, so it can describe a smaller job than the one that was agreed — and an agent reading only the mirror builds the smaller thing. `AGENTS.md` and `CLAUDE.md` both point at Linear, and `CLAUDE.md` adds that the issue's status is kept honest as the work moves, since closing the GitHub issue does not close the Linear one.

### Fixed

- The Playwright suite no longer reuses whatever web server happens to be listening. Reuse skipped the production build the run is supposed to test, so anything already on the port — an `astro dev` server, or a leftover preview from an earlier run — stood in for it, and the suite reported on a stale `dist/`. That surfaces either as failures that look like test bugs and are not, or, worse, as passes. A port already in use now fails the run instead.
- The default port for that server moved off 4321, which is the one `astro dev` and `astro preview` use, so a dev server and the test server no longer compete for it. `PLAYWRIGHT_PORT` still overrides it.

## [0.8.0] - 2026-09-07

### Added

- **Extract Archive** opens a ZIP on your device and shows what is inside it: every file, in its folders, with its size and how it was packed. Tick what you want and take it out — one file comes back as itself, several come back as a ZIP of just those. Nothing is uploaded, including the list of names inside, which is often the part that says the most.
- It reads the archive with the decompressor the browser already has, so it adds no dependency, and it reuses the ZIP machinery Create ZIP writes with rather than growing a second stack beside it. Encrypted entries and entries packed with a method no browser can read are listed with the reason on the row rather than silently skipped; a path written to unpack outside its folder is corrected and shown as it was stored; two entries wanting one name are numbered rather than one replacing the other; and every file is checked against the archive's own checksum before it is handed over.
- RAR and 7z are recognised and named rather than failing vaguely. Reading either needs a decoder that is not part of this site, which is a decision about a dependency rather than a small change, so it has not been made quietly.
- **URL Encode & Decode** turns text into the percent-encoded form a URL can carry, and turns it back, as you type. It asks which of the three encodings you mean rather than picking one quietly: a value going inside a URL, a whole address that is already assembled, or a form field — which is the only one where a space is written as a plus, and the only one that reads a plus back as a space. That last distinction is what keeps a base64 string from being quietly corrupted.
- Decoding says **where** a broken escape is. The browser's own decoder throws the same error for every kind of broken input and never says which character; this one walks the text and reports the position and the reason — an escape cut off by the end of the text, a per-cent sign followed by something that is not hexadecimal, or bytes that are legal escapes and still not a character in UTF-8, including the overlong and surrogate spellings that a decoder counting only bytes would accept.
- Swap puts the result back into the box and turns the direction round, so a round trip can be checked in one click. Nothing is uploaded: the conversion is a function running in the page.

### Changed

- Two roadmap phases are behind us, and the roadmap says so. **The PDF page tree** shipped whole: reordering and rotating pages, a watermark, page numbers, a signature you drew yourself, and clearing the fields a document carries about whoever made it. Its standing records what the shared machinery actually bought — a page that arrives carrying its own rotation is displayed with its sides swapped, and the one correction for that is written once and used by the watermark, the page numbers and the signature alike — and the work the phase made for itself, which is that every Gizlet after it has to expect a sideways page.
- **One archive, three uses** is behind us too, ahead of its place in the order, because none of its three Gizlets needed anything that was not already here. Its own stopping condition is the one on that page which actually ran: reading a RAR needs a decoder that cannot be justified, so the phase shipped the ZIP half and dropped the rest rather than carrying it.
- **Text in, text out** becomes the next phase: the small conversions and inspections that are a single pure function each. The first of them is in this release.
- The sitemap now tells crawlers when each page last changed. Every entry in `/sitemap.xml` carries a `<lastmod>`, and the dates are real ones: they come from the git history of the files behind each page, so the privacy policy is dated the day its wording changed and a Gizlet is dated the day its workspace did, rather than every page claiming to have changed on the day the site was last built. A sitemap that says everything changed at once says nothing, and a crawler learns to disregard it.
- `pnpm run sitemap:dates` prints the dates, `--write` regenerates them, and `--check` verifies them. Regenerating is a step in the release procedure, and the `Release` workflow fails a release whose dates are stale — it is the only job with the full history to check them against.

## [0.7.0] - 2026-09-06

### Added

- **Clean PDF Metadata** lists what a PDF says about itself — title, author, subject, keywords, the software that wrote it and when — and then writes a copy with those fields cleared and the XMP packet dropped, entirely on this device. The pages are untouched, the copy is read back to say what it carries, and the page is explicit that this does not touch what is on the pages.
- **Create ZIP** bundles files, or a whole folder, into one standard archive on this device. Folder structure is kept, two files with the same path are numbered rather than one silently overwriting the other, and the order is yours to change before you build it. Each file is deflated with the browser's own compressor, or stored when compressing it would make it larger.
- **Favicon Generator** turns one picture into the icon set a site needs: `favicon.ico`, PNGs at 16, 32, 180, 192 and 512 pixels, the HTML for the page head and the icons fragment for a web app manifest — as one ZIP, made on this device. Each size is previewed at the size it will really be, a picture that is not square gets an explicit choice between cropping and fitting, and the ICO is assembled from PNGs so it stays a few kilobytes.
- **Start from the file.** Drop an image or a PDF on the home page and Gizlet says what it is and which Gizlets take it, derived from the same input contracts the flow builder uses rather than from a list kept by hand. Picking one opens it with the file already chosen: the file is kept in this browser's own storage for the length of a page load and deleted as it is read, so nothing is uploaded and nothing is asked for twice.
- **Compress, Resize and Convert now take a batch.** Choose or drop up to 25 images, set the controls once, and every picture is processed on this device in turn — each with its own download and all of them as one ZIP. A file the browser cannot decode costs that one row rather than the run.
- **Image Flows run over a batch too.** An image flow accepts several starting pictures whatever its chain, runs every step over each of them, and hands back the set as one archive. A picture a step cannot do is listed with its reason beside the ones that finished.
- **Organize PDF** rebuilds a document by its pages, on your device. Every page is drawn as a card you can drag somewhere else, turn a quarter at a time, copy, or drop, with the new order shown as you build it — and every drag has a button beside it, so a whole document can be reordered from the keyboard. Tick pages to act on several at once, or to extract them into a document of their own. A turn is added to the way a page already sat rather than replacing it, so a sideways scan comes upright in one press. Saving writes a new PDF holding the pages exactly as they sit on screen; the file on your device is never touched, and the pages are copied rather than redrawn, so text stays selectable and nothing is re-encoded.
- **PDF Page Numbers** writes numbers onto a document that arrived without them: four formats, six positions — all of them edges, because a page number in the middle of the page is not a page number — with a size, a margin, the number to start at, pages to skip at the front, and a range. The numbers are drawn onto the existing pages rather than rebuilt, so text stays selectable and nothing already on the page is touched, and your original file is not modified.
- The three settings about counting compose in one order, and the preview shows the result before anything is written: the skipped pages go first, the range narrows what is left, and numbering counts from the starting number across whatever survived. Numbering pages 5 to 8 starting at 1 gives 1 to 4, because that is what was asked for rather than an offset to work out, and a total such as "of 10" counts the numbers actually printed.
- **Every PDF Gizlet now reads documents through the same viewer.** The PDF Viewer stopped being a one-off and became the document surface for the whole PDF half of the site: thumbnails, page navigation, a page field, zoom and full screen, learned once and found everywhere. Image to PDF previews the document it generated, PDF to Image shows the source while pages are chosen, and Merge and Split can each inspect a document going in or coming out without leaving the Gizlet.
- **Full screen is new, and it never does nothing.** Where the browser has element full screen it uses it, with the platform's own exit gesture; where it does not — most iPhones — the same layout fills the viewport and Escape leaves it. The document, the page and the zoom survive the move both ways, and the page is redrawn at the size it now has rather than stretched.
- Every PDF page now loads about a megabyte lighter: the PDF renderer arrives only once there is a document to draw, on every PDF Gizlet including the reader itself.
- **Sign PDF** places a visible signature on a document, entirely on this device. Draw it with a pointer, type your name, or choose a picture of one; drag it to the line it belongs on, size it against the page, and name the pages it goes on. It says plainly, on the page and in its result, that this is a drawing rather than a certificate-based or cryptographic signature.
- **Watermark PDF** stamps text or a picture across the pages you name, on your device. Set the position, size, turn and strength and the mark is shown over the real page before anything is written — drawn from the same placement the document is written with, so the preview is where it goes rather than an impression of it. The mark is drawn onto the pages rather than the pages rebuilt, so the text under it stays selectable and the file barely grows. A page carrying its own rotation is corrected for: a sideways scan is displayed with its sides swapped, and a mark placed in the corner you are looking at lands in that corner.
- A visible watermark marks a document; it does not protect one. Nothing on the page claims otherwise, and the questions on it say so plainly.

### Changed

- The ZIP writer now takes a deflated payload per entry as well as a stored one, so an archive of text is smaller while an archive of already-compressed pictures stays exactly as it was.
- Resize applies one set of numbers to a batch the way each picture needs it: a percentage scales every picture, an exact width with proportions kept lets each picture work out its own height, and turning proportions off forces every picture to the same box. The workspace says which of the three is about to happen.

## [0.6.0] - 2026-09-05

### Added

- Image Background is built. Put a picture on a canvas you choose — a size, a colour behind it or none at all, how the picture is scaled into it, and where it sits — drawn and encoded by your own browser with nothing uploaded. The presets are the shapes the job asks for: the picture's own size, a 1080 square, a 1200 by 630 link preview, a 1080 by 1920 story, and any size you type. Fit inside keeps the whole picture with background around it, Fill the canvas covers the frame and trims the overflow, and Original size leaves every pixel alone, which is what adding a border needs. Nine anchors decide where the picture is held, and two nudge fields move it from there.
- A transparent background stays transparent in PNG and WebP, and the page says what JPEG will do to it before the download rather than after: JPEG cannot hold transparency, so it is saved white — a canvas flattens to black otherwise, which is nobody's idea of a background. The preview sits on a checkerboard, so "no background" looks like no background instead of like white. Typing a canvas size moves the preset to Custom rather than leaving the control claiming a shape the fields no longer hold.
- Image Background is a Flow block. A canvas the size of the picture would be a block that does nothing, so a flow starts at a 1080 square and carries the canvas and the fit in its recipe link — the colour, the position and the nudges are taste, and a colour would also be the one value the link format could not carry as a whole number or a name from a closed list.
- Image Color Picker is built. Pick a pixel out of a picture and read it as HEX, RGB and HSL, each copyable — drawn onto a canvas and read one pixel at a time by your own browser, with nothing uploaded and no file written. Click or tap a pixel, drag to keep picking as you sweep across an area, or focus the picture and move with the arrow keys: one pixel a step, ten with Shift, stopping at the edge. It opens on the middle pixel, so there is always a colour to move from rather than an empty panel to aim at.
- The colours picked during a visit sit underneath, newest first, each copyable by clicking it. Picking the same colour twice moves it rather than filling the row with one mistake. They live in the page and nowhere else: closing the tab forgets them, and nothing is written to browser storage or sent anywhere.
- A grey is reported with a hue of zero, because every hue produces a grey once the saturation is gone and naming one would be inventing it. The swatch decides whether to print its own hex in dark or light text by relative luminance rather than by lightness, which is the difference between a readable label on yellow and a white one.
- Image Dimensions is built. Drop a picture in and it says how many pixels across and down, what aspect ratio that works out to, how many megapixels, whether it is landscape or portrait, what the file actually is, and how big it is — read by your own browser, with nothing uploaded. It writes no file at all: there is not even a download, because nothing was made. The dimensions, the ratio and each side on its own carry a copy button; the word "Landscape" does not, because nobody pastes that into a form.
- The aspect ratio is the part worth doing properly. Sides that divide into something recognisable are printed as they are — 1920 by 1080 is 16:9. Sides that reduce to a fraction nobody could use are named after the shape the picture is within one percent of, marked with a ≈, and a picture near no common shape is given as a decimal rather than as a ratio that would be technically true and practically useless.
- It is the second Gizlet with no place in a Flow, alongside the PDF viewer, and says so in the same list rather than being given a pass-through contract it does not have: it shows you something and produces nothing another Gizlet could take.
- Remove Image Metadata is built. It reads what a picture says about you — GPS coordinates, camera make and model, lens, timestamps, software, owner and serial number — shows them grouped with the location first and in red, and then strips the lot by redrawing the picture and encoding it fresh. The reading is done by a parser that ships with the page: no upload, and no library fetched to inspect your file, which would rather defeat the exercise for a photograph carrying your address.
- The claim is checked rather than asserted. After cleaning, the file that is about to be downloaded is read back with the same parser, and the result panel says what that second read found. Entries the page has no name for are counted rather than hidden, so the summary never suggests a file carries less than it does, and a file with nothing to remove says so plainly instead of pretending to work.
- The picture is drawn exactly as the browser displays it, so a photograph that arrived upright stays upright even though the orientation tag that asked for it is gone — a quarter-turned JPEG comes out the way you saw it, not the way it was stored. Remove Image Metadata is also a Flow block, so a chain can strip a file on its way to anywhere else.
- Rotate & Flip Image is built. Turn a picture in quarter turns, mirror it left to right or top to bottom, and download it — decoded, redrawn and encoded by your own browser, with nothing uploaded. The sides swap after a quarter turn, so a 4000 by 3000 photograph rotated right is 3000 by 4000, and the panel says so before you save. The preview is the transform itself drawn on a canvas rather than a stylesheet tilting the picture, so what is on screen is what the download holds.
- Every press folds into one of eight orientations rather than stacking transforms. Four rotations bring the picture back to where it started, a flip pressed twice returns exactly, and the original pixels are drawn once when you save — so pressing a button ten times costs the picture nothing. A flip mirrors what you are looking at even when a rotation is already applied, which is the part that usually drifts. "Put it back" is available only once something has actually changed.
- Rotate & Flip Image is a Flow block. A flow has nobody to press a button until it looks right, so the block names one turn — rotate left or right, upside down, or either mirror — and every image the flow is carrying gets it, with the sides swapped for the block that follows. A recipe link carries the named turn rather than a state nobody chose.

### Changed

- The roadmap's image phase is behind us. All seven Gizlets it committed to are built — cutting a picture down, arranging several into one, turning one upright, setting one on a background, reading what a photo says about you and stripping it out, and reading a colour or a size back off an image — so the phase reads SHIPPED and says where it stands in the past tense, as the page's own rule requires. The PDF page tree becomes the next phase, with the dependency it has always named: the viewer becoming a surface the other PDF Gizlets can reuse.
- The standing says the awkward part rather than skipping it: the kill criterion never got to run, because the phase was built inside the window it was meant to be judged in. That is the honest reading of it, and it is not a claim that demand was proven.

### Fixed

- Search no longer returns nothing because the query had a verb in it. The field is labelled "I need to…" and then rejected the words that answer it: `make JSON-LD`, `write JSON-LD`, `add structured data`, `format my JSON` and `tidy JSON` each found nothing, because every term had to match and a catalogue of nouns contains no verbs. The site's own JSON-LD Generator was unreachable by the most natural way to ask for it. A Gizlet is now scored over the terms it matches, and the ones matching the most terms are returned — so `compress photo` still returns only Compress Image, though Resize Image knows "photo", and `i need to crop my photo` finds Crop Image. A result must still answer at least half of what was asked, so `make a qr code` says so rather than offering Collage Maker for the word "maker".
- A search term now matches a word rather than the letters inside one. `peg` matched every JPEG Gizlet and `son` matched both JSON ones, which is the same accident that let `a` and `an` match everything on the site while `some` and `make` matched nothing — behaviour nobody chose. A term still matches from the start of a word, because the field is searched as it is typed and a half-typed word is the normal case.

## [0.5.0] - 2026-09-05

### Added

- Collage Maker is built. Choose up to twelve pictures, put them in the order you want, and get one image back — arranged, drawn and encoded by your own browser, with nothing uploaded. Four arrangements: a grid as square as the count allows, a single row, a single column, and a feature that gives the first picture two thirds of the width and stacks the rest beside it. The gap between pictures, the colour behind them, the finished width and the output format are all yours; the height follows from the arrangement, so a taller collage makes a taller file rather than a squashed one. Cells are filled rather than fitted, which is why no cell arrives with two bars of background beside it.
- The preview is not a mock-up of the collage: it is the collage, drawn at full size and shown smaller, so what gets downloaded is the drawing that was already on screen. The pixel limits the other image Gizlets keep are checked against the whole composition rather than against each picture going into it, because twelve pictures that are individually fine still add up, and the canvas that fails is the combined one.
- Collage Maker is a Flow block, and the first one that turns several images into a single image. A flow now takes its ceiling from the combining block in the chain rather than from the category holding it — assembling pages and arranging a collage are different jobs with different numbers of pictures — and a block that combines says what it actually produces, so a collage block reads "one image" where the PDF block reads "one PDF". A recipe link carries the arrangement; the gap, the colour and the width are taste, and a link does not carry taste nobody chose.
- Crop Image is built. Drag a rectangle over the picture, or type its left, top, width and height in image pixels, and download just that part — decoded, cut and re-encoded by your own browser, with nothing uploaded and the uncropped original never leaving the tab. Aspect ratio presets lock the shape to a square, the two photographic ratios, widescreen, or any of those turned upright, and free crop takes whatever shape you draw. The selection is keyboard-operable in its own right: arrow keys move it, Alt with an arrow key moves it a single pixel, and Shift with an arrow key resizes it, keeping a locked shape as it goes. A selection that runs off the edge of the picture stops at the edge instead of collapsing, a zero-area one is refused with a reason, and the pixel ceilings the other image Gizlets keep are kept here too.
- Crop Image is a Flow block, so a chain can crop between any two image steps. A flow has nobody to drag a rectangle, so the block asks for a shape instead and takes the largest rectangle of it from the middle of the image — the same crop the workspace opens on when you pick that ratio and touch nothing else. A recipe link carries the shape, spelled `16x9` rather than `16:9`, because the link format's own delimiters are the reason it has never had to percent-encode anything.
- A `/roadmap` page says what Gizlet is building next and what would make it stop. Seven phases each fill in the same short form — when, what, what it reuses, the one signal Gizlet can actually watch, and the condition under which the work does not happen — so two phases can be compared by reading the same line twice instead of by trusting two differently shaped paragraphs. There is no timeline, connector, dot, gantt or card anywhere on it, and that is the point: every one of those shapes implies a date this project does not have, and a reader who infers one has been misled by the layout rather than by the prose. A phase's "when" is a dependency; the only statuses are behind us, next, and later. It ends with a table of four things Gizlet will not build, each carrying somewhere else to go, closing on the rule that generates the list: if it needs a server, it isn't a Gizlet.
- The Gizlet index now shows the bench. "Not built yet." — not "Coming soon", which promises — lists twenty-five Gizlets grouped by category with a count each, on dashed rules against the solid ones the working Gizlets use. A row on the bench is not a link, so there is no whole-row pointer inviting anyone to a page that does nothing; it carries exactly two, the phase that explains the order and a request that turns a reader into the one signal this project can count. A working Gizlet's row now prints its registry number, which is what makes the em dash beside an unbuilt one mean something. The request line is the last thing on the page, and it says plainly that a request opens a public GitHub issue in your name, and that we count issues rather than clicks.
- Asking for a Gizlet from the bench is one click. The row's link names it, the form resolves that name against the registry and prefills the idea field from the registry entry, and the issue takes a fixed title so demand is countable by a title search rather than by reading issue bodies. A name the registry does not carry is ignored outright rather than echoed back: the prefill ends up in an issue filed in the visitor's own name, so a crafted link must not be able to put someone else's text there. Rewrite the idea and the request becomes your own, titled as one. The value never leaves the browser, and query strings are not logged.

## [0.4.0] - 2026-09-04

### Added

- Gizlet Flows can turn a document back into images. A chain that reaches PDF to Image converts every page, runs each later block once per page, and finishes with a set: a row per image with its own download, and one archive holding all of them, so the promise of one download at the end still holds. It needed no edit to the flow graph — the Gizlet declares `pdf-file` in and `image-file` out, and the payload-kind rule already said what that means. A Gizlet that reads a document is reachable after Image to PDF, with a merge the exception, because there is nothing to join a lone document to.
- A splitting step in the flow contract, the counterpart of the combining step Image to PDF and Merge PDF declare. A chain knows whether it ends with one file or a set because the step says so, rather than because the payload kinds were read as implying it, and the last step of either kind is the one that decides — so a chain that takes a document apart can combine it again, and the rule that keeps a merge out of a chain holding one file needed no exception written into it.
- A recipe link can carry a PDF to Image block, including its resolution. Which pages to convert is deliberately not carried: every other value in the format is a whole number or one of a closed list of names, and a page range would be the one key that could hold free text, so a shared flow converts the whole document.
- A Merge PDF Gizlet: choose two or more PDFs, arrange them, and download one document holding every page of every file in that order. Each document is opened by this browser as it is chosen, so the list shows its page count before anything is joined, and pages are copied rather than redrawn — text stays text, a scan keeps its resolution, and a merged document may hold pages of different sizes. Nothing is uploaded, which is the point: the documents people join are usually the private ones, an identity paper with a proof of address, a payslip with a bank statement. A password-protected PDF is refused by name, because its pages would copy as ciphertext without the password, and so is a file that is a PDF in name only. One merge takes up to 20 documents and 500 pages, the same 500 the PDF Viewer will open, and reports its progress past 50. The merged file is drawn in the page before it is downloaded, with pdf.js arriving only once there is something to draw. It needed no new dependency: `pdf-lib`, already here for Image to PDF, copies a page tree as readily as it writes one.
- A PDF is now shown in the page before anything is downloaded, both on the Image to PDF Gizlet and in a flow that ends in one. The result panel draws the assembled document page by page, with previous, next, and a page jump, so the page order, the page size, and what automatic orientation did to each sheet are all visible while there is still time to change them, instead of having to download the file to find out. It is the finished document that is drawn, not a re-rendering of the source images, and the page turning is the shared `src/scripts/pdf-page-view.ts` the PDF workspaces already use. pdf.js is loaded only once a PDF exists, so neither page's initial JavaScript changes for a visitor who never makes one, and a preview that will not draw says so and leaves the download alone, because a document can be perfectly good even when drawing it is not.
- A PDF to Image Gizlet, at `/tools/pdf-to-jpg/`: open a PDF, choose the pages, a JPEG, PNG, or WebP format, and 72, 144, or 216 dpi, and get one image per page. The document is drawn beside the controls while the pages are being chosen, so a page can be found rather than guessed at, and every page arrives with its own download alongside a single archive of the whole set. Reading the PDF, drawing each page, encoding the images, and packing the archive all happen in this browser, which matters because the pages people most often need as pictures — a scanned contract, a medical letter, an identity document — are exactly the ones that should not be handed to a conversion site. It is called PDF to Image rather than PDF to JPG for the reason Image to PDF was renamed: it writes three formats, and naming one of them would be the same inaccuracy in the other direction. A password-protected PDF, a file that is not really a PDF, and a document that reports no pages are each explained rather than left as a dead button, and one hundred pages is the ceiling for a single pass.
- `pnpm run pr:assets -- <image>…` publishes a pull request's screenshots to the `pr-assets` branch and prints the markdown that embeds them. The screenshot rule in [AGENTS.md](AGENTS.md) already said where those images live; getting them there by hand was a dozen git plumbing calls, rediscovered on every pull request. The script checks nothing out and switches no branch, and commits on top of what the branch already holds, so another pull request's images survive.
- A Split PDF Gizlet, at `/tools/split-pdf/`: open a PDF and either name the ranges you want — `1-3, 5, 8-10` gives three documents — or ask for every page separately and get one PDF per page. The document is drawn beside the field while the pages are being chosen, so a range can be found rather than guessed at, and each part arrives with its own download alongside a single archive of the whole set. The pages are copied rather than redrawn, so what comes out is the same PDF content it went in as: text stays selectable, fonts stay embedded, and nothing is re-encoded. Splitting is usually the step before sending part of a document on, which is exactly when the file on the device is a contract, a payslip, or a medical letter, so reading the PDF, writing each new document, and packing the archive all happen in this browser. A range that runs backwards, a page past the end, or the same range written twice is refused rather than guessed at, and a password-protected PDF, a file that is a PDF in name only, and a one-page document that has nothing to split into are each explained rather than left as a dead button. Documents of up to 500 pages, the same 500 the PDF Viewer will open, so anything this Gizlet produces can be read in the one next to it. It needed no new dependency: `pdf-lib`, already here for Image to PDF and Merge PDF, copies a page tree out as readily as it copies one in.
- Gizlet Flows can now split a document mid-chain. A flow carries a set of PDFs rather than a single one, so a Split PDF block takes the document apart into its pages and every block after it runs over each piece: images can become a PDF, be split back into pages, and be converted to images again in one pass. A set of documents finishes as one archive, the same way a set of images already did.
- `src/data/zip-archive.ts`, a ZIP writer of about a hundred lines, so a Gizlet that makes a set of files can offer one download. The entries are stored rather than deflated, because a JPEG, a PNG, or a WebP is already compressed and deflating one spends time to save nothing — which is what lets the format be written without a compressor and without a dependency. Every entry carries the same fixed 1980 timestamp instead of the clock, so an archive built twice from the same files is byte for byte the same and the download says nothing about when or where it was made.

## Release policy

- Releases use `MAJOR.MINOR.PATCH` version numbers.
- Before `1.0.0`, a minor version may introduce breaking changes; patch versions are for backward-compatible fixes.
- The first usable public release will be `0.1.0`.
- Changelog entries describe user- or contributor-visible changes. Internal maintenance that has no meaningful external impact does not need an entry.
